# Skill Mesh Balance

`$docara` owns the standalone Docara 2 product contract: project discovery and
initialization, JSON schemas and inheritance, content-to-route behavior,
locales, navigation, typed Document IR, component admission, design
composition, build/preview/verification, Developer/AI SDK integration,
transactional engine update, package preparation, and static publication
handoff.

## Companion ownership

- `$docs` owns documentation method, audience design, information
  architecture, documentation maps, editorial review, and screenshot-driven
  authoring. `$docara` implements the resulting site mechanics.
- `$content` owns large-scale writing, normalization, migration, localization,
  and content QA. `$docara` owns valid Markdown, route, locale, component, and
  build integration.
- `$seo` owns public search visibility, canonical/title/H1/meta, structured
  data, robots, and sitemap decisions. `$docara` owns available static fields,
  routes, canonicals, redirects, and verified output.
- `$ux` owns reader journeys, hierarchy, discoverability, responsive behavior,
  and interface acceptance. `$docara` owns admitted layouts, regions,
  preferences, and components.
- `$tester` owns QA evidence and acceptance verdicts. `$docara` supplies
  deterministic builds, receipts, preview targets, static verification, and
  reproduction details.
- `$ops` owns hosting, access, backups, rollback, traffic switching, incidents,
  and live deployment.
- `$dev` owns implementation in the Docara engine repository. `$docara` owns
  the product-specific contract and expected project behavior.
- `$graph` owns capability structure, relations, readiness, and generated
  context. It does not replace this skill's domain method.
- `$teamlead` coordinates multi-stage, multi-owner, release, or migration work.

## Routing rules

- Keep a narrow content or setting edit inside `$docara` unless editorial,
  SEO, UX, or QA judgement is genuinely required.
- Use `$docs` or `$content` for substantial content sets rather than turning
  `$docara` into a general writing methodology.
- Use `$dev` when engine `src/`, package schemas, bundled registries, or product
  tests must change.
- Use `$tester` for browser matrices, structured QA, regression, or readiness.
- Use `$ops` before any live/static-host mutation.
- Use `$teamlead` when the work crosses project migration, package release,
  deployment, and acceptance boundaries.

## Handoff

Provide the goal, project root, exact package/source revision, changed owner
files, effective setting provenance, component/design IDs, commands executed,
output path, receipts, verification result, browser/QA evidence, blockers, and
the smallest next owner action.
